1. Visão geral

O Trabalho 3 resolveu a persistência: os dados agora sobrevivem ao fechar o app, usando Room. Mas a
forma como isso foi feito mistura tudo — a tela (o @Composable) fala direto com o @Dao, dispara a
CoroutineScope sozinha, e guarda o estado da UI espalhado em várias variáveis remember. Funciona,
mas cresce mal: quanto mais telas e regras o projeto ganha, mais difícil fica mexer em uma parte sem
quebrar outra.
O Trabalho 4 não pede nenhuma tela nova, nenhuma funcionalidade nova. O trio vai pegar exatamente o
que já existe — as mesmas Entities, o mesmo DAO, as mesmas telas — e reorganizar em MVVM (Model
— View — ViewModel): um padrão de arquitetura que separa a lógica de dados, o estado da tela e a
interface em camadas bem definidas. O trio já viu a base disso na Aula 12 — Navigation (um ViewModel
simples guardando estado) —, aqui essa ideia evolui com Repository, StateFlow/UiState e
ViewModelFactory.
É um trabalho de refatoração, não de criação — e isso é proposital: reorganizar código que já funciona,
sem quebrar nada, é uma habilidade tão importante quanto escrever código novo.

3. Requisitos técnicos

3.1 Organização em pacotes
O código do Trabalho 3 provavelmente está todo meio junto (telas, Entity, DAO, Database no mesmo lugar
ou em pastas soltas). Agora ele precisa ficar organizado em pacotes com responsabilidade clara:
• ui — as telas (@Composable), sem nenhuma lógica de banco ou de regra de negócio dentro delas.
• data (ou data.local) — as @Entity, o @Dao e a classe @Database do Room, exatamente como
já existem do Trabalho 3.
• data.repository — os novos Repository (seção 3.2).
• viewmodel — os novos ViewModel, UiState e ViewModelFactory (seções 3.4 e 3.5).
• No mínimo esses 4 pacotes, com os arquivos movidos para dentro deles — não basta criar as pastas
vazias.

3.2 Repository: a única fonte de verdade
Hoje, quem chama o @Dao é a própria tela. Isso muda: a tela nunca mais fala direto com o DAO — só o
Repository fala com o DAO, e só o ViewModel fala com o Repository.
• No mínimo 1 Repository por Entity (mesmo mínimo de 2 Entities do Trabalho 3) — ex.:
FilmesRepository, que recebe o FilmesDAO no construtor e expõe funções como
buscarTodos(), inserir(...), atualizar(...), deletar(...), simplesmente repassando
para o DAO por baixo.
• Motivo: se um dia os dados vierem de outro lugar além do Room (uma API, por exemplo), só o
Repository muda — ViewModel e tela continuam intactos.

3.3 DAO reativo com Flow
Hoje, a tela busca os dados uma vez (geralmente num LaunchedEffect(Unit)) e precisa se lembrar
de buscar de novo depois de cada inserir/remover. Isso também muda:
• A função de buscar todos no @Dao passa a retornar Flow<List<...>> em vez de uma lista simples
— por exemplo, @Query("SELECT * FROM filmes") fun buscarTodos():
Flow<List<Filmes>> (repare que não é mais suspend fun, porque Flow já é assíncrono por
natureza).
• Com isso, o Room atualiza esse Flow sozinho sempre que a tabela muda — inserir, atualizar ou
deletar um item atualiza a lista automaticamente, sem precisar buscar de novo na mão.

3.4 ViewModel com UiState
Esta é a parte central do trabalho. No mínimo 2 ViewModel (um por Entity/tela principal), cada um
estendendo ViewModel() e seguindo este padrão:
• Uma data class ...UiState agrupando tudo que aquela tela precisa para se desenhar (a lista
de itens, o texto do formulário, se está carregando, etc.) — em vez de várias variáveis remember
soltas.
• Dentro do ViewModel, duas variáveis para o mesmo estado: private val _uiState =
MutableStateFlow(FilmesUiState()) (privada, só o ViewModel modifica) e val uiState:
StateFlow<FilmesUiState> = _uiState.asStateFlow() (pública, só leitura — a tela
observa, nunca altera direto).
• Métodos de ação chamados pela tela (ex.: adicionarFilme(...), removerFilme(...)) que
chamam o Repository dentro de viewModelScope.launch { ... } e atualizam o _uiState
com o resultado.
• A tela passa a só fazer duas coisas: coletar o uiState (com collectAsStateWithLifecycle()
ou collectAsState()) para saber o que desenhar, e chamar os métodos do ViewModel quando
o usuário interage. Nada de dao, CoroutineScope ou Dispatchers.IO dentro do @Composable
— isso tudo já vai estar dentro do ViewModel/Repository.

3.5 ViewModelFactory
O Android não sabe criar um ViewModel que recebe parâmetro no construtor (no caso, o Repository)
sozinho — por isso cada ViewModel precisa de uma Factory:
• No mínimo 1 ViewModelFactory por ViewModel (ou uma só reaproveitada, se fizer sentido),
implementando ViewModelProvider.Factory, repassando o Repository certo para o
ViewModel na hora da criação.
• Na tela, o ViewModel passa a ser obtido com viewModel(factory =
FilmesViewModelFactory(repository)) em vez do viewModel() simples visto na Aula 12.

3.6 O que não pode mudar
Nenhuma tela nova, nenhum campo novo, nenhuma funcionalidade nova. O app precisa continuar
fazendo exatamente o que já fazia no Trabalho 3 — adicionar, listar, atualizar, remover, persistir — só que
agora organizado em camadas. Se alguma funcionalidade quebrar durante a reorganização, é isso que
será testado na apresentação.

4. Documentação do processo e das decisões
Mesmo padrão dos trabalhos anteriores: o foco principal é mostrar o app funcionando de verdade —
prints e, principalmente, vídeos curtos — não só texto. No próprio repositório, num arquivo README.md
(podendo continuar sendo em um Google Slides, com o link no README), respondam com suas palavras,
ilustrando com prints/vídeo:
• Como estava o projeto no Trabalho 3, e o que mudou na reorganização?
• Como o trio decidiu dividir os pacotes — o que foi para ui, data, data.repository e
viewmodel?
• Por que o Repository existe — o que ele resolve que não existia antes?
• O que tem dentro do UiState de cada tela, e por que escolheram esses campos?
• Alguma funcionalidade quebrou durante a reorganização? Como encontraram e corrigiram?
• Algum integrante do trio teve dificuldade em algum ponto? Como resolveram?

5. Como entregar
• Continuar no MESMO repositório do Trabalho 3 (não precisa criar um novo — é o mesmo app,
reorganizado).
• O repositório precisa conter tudo que é necessário para rodar o projeto, mais o arquivo de
documentação da seção 4.
• Sem commits após o prazo combinado em sala (data de entrega definida no Blackboard da turma).
• Apresentação rápida em sala mostrando o app funcionando exatamente como no Trabalho 3 (nada
quebrou), e explicando onde ficou cada camada: Model, Repository, ViewModel, View.

6. Checklist rápido antes de entregar
• [ ] Código dividido em pelo menos 4 pacotes: ui, data, data.repository, viewmodel
• [ ] Existe no mínimo 1 Repository por Entity, e só ele fala com o DAO
• [ ] O buscarTodos() do DAO retorna Flow<List<...>>
• [ ] Existem no mínimo 2 ViewModel, cada um com seu próprio UiState
• [ ] Cada ViewModel usa o padrão _uiState privado + uiState público (StateFlow)
• [ ] Existe no mínimo 1 ViewModelFactory, injetando o Repository no ViewModel
• [ ] As telas não têm mais dao, CoroutineScope ou Dispatchers.IO diretamente — só leem
uiState e chamam métodos do ViewModel
• [ ] Testei: o app continua fazendo tudo que fazia no Trabalho 3 (adicionar, listar, atualizar, remover,
persistir)
